# 与 GitHub 上的 ASCII 生态对比 —— 基于实测，不是印象

## 先说清楚可比性 —— 这是最重要的一点

GitHub 上的 ASCII 项目绝大多数在解决**另一个问题**：

| 项目类型 | 代表 | 它在做什么 |
|---|---|---|
| 媒体转码 | [d4rkf0x/ai-ascii-film](https://github.com/d4rkf0x/ai-ascii-film) | 把**已有的**图像/视频转成 ASCII |
| 实时特效库 | [p5.asciify](https://relatedrepos.com/gh/humanbydefinition/p5.asciify) | 在 p5.js 里实时把画面转成字符 |
| GPU 着色器 | [js-shaders](https://relatedrepos.com/gh/danthedaniel/js-shaders) | GPU 光栅化字符，追求帧率 |
| 字符网格绘图 | [typograms](https://www.libhunt.com/compare-typograms-vs-goat) | 用字符画**图表** |
| 终端动画 | [ascii-motion](https://pypi.org/project/ascii-motion/0.2.0/) · [terminal-ascii-art](https://pypi.org/project/terminal-ascii-art/0.1.1/) | 在终端里播放/渲染 |

> **它们把世界变成字符；我们让字符自己演一部电影。**
> 这不是「谁更好」，是**受众与问题都不同**：前者给开发者，后者给导演。

**诚实声明**：我**没有实测**这些项目在同样内容上的画面质量，也没有基准图。
下面的质量对比是**基于架构的判断**，不是测量结果。凡是我们这边的数字，都是实测的。

---

## 我们这边的实测（DRAFT-T2，全部来自解码像素）

| 指标 | 值 |
|---|---|
| 分辨率 / 帧率 / 时长 | 1920×1080 · 30fps · **480 帧 / 16.000s** |
| 网格 | **240×120 = 28,800 格**（每帧字符构成） |
| 墨覆盖 最小 / 平均 / 最大 | **0.0014 / 0.1248 / 0.2944** |
| 峰值帧 | **292**（碎裂段 291–350 内 ✅） |
| 输出 | 9.65 MB · sha256 `4a6f6daf…` |

**与 V1 研究（同网格）对比**：

| | 墨覆盖 |
|---|---|
| V1 A 雕塑 | 峰值 **0.4608** |
| V1 C 字段 | 0.0029 → 0.2506 |
| V1 B 空间 | 恒定 0.0350 |
| **DRAFT-T2** | 平均 **0.1248**，峰值 **0.2944** |

→ **DRAFT-T2 的平均密度已进入 V1 A 的区间**（A 的帧 44 为 0.2173），但**峰值仍低于 A 的 0.4608**。

## 我们的真实优势（架构性，可核实）

1. **对象身份贯穿全片。** 转码器是**无状态**的——每帧独立把像素变成字符，没有「这个字符上一帧在哪、属于谁」。
   我们的引擎里每个字符有 identity、有 provenance、能跨越碎裂存活。**这是转码器架构上做不到的。**
   正因为有它，才能做 `接缝张开 → 碎裂沿拓扑扩散 → 重组成新结构` 这种**有因果的形变**。
2. **导演级契约 + 编译期验证。** 镜头动机、因果对、跨剪辑状态连续都由编译器强校验——我这一轮就用错一个表达式类型被拒绝过。
3. **确定性可复现。** 重复渲染字节一致，实测过多次（重建 R3.7.1 得到相同哈希）。
4. **可审计的层账本。** 每帧每层的「画了多少 / 到达画面多少 / 被遮多少」都有记录——这一轮正是靠它定位了故障。
5. **518,975 条不变量断言 + 54 个 gate。**

## 我们的真实劣势（同样明确）

1. **不能转码任何输入。** 这是最大的功能性劣势——喂一张图给这个引擎毫无用处。GitHub 工具的核心能力我们**完全没有**。
2. **不是库、没有生态。** 没有 npm 包、没有 API、没有 star、没有贡献者、没有示例。学习曲线极高。
3. **没有实时、没有 GPU。** 离线确定性渲染，480 帧要几分钟。着色器类项目是毫秒级。
4. **视觉质量未被任何人认可。** 外部导演对含人形那版的结论是 `HUMAN RECOGNITION: NOT VALIDATED`；
   DRAFT-T2 **我还没请人看过**。
5. **只服务 ASCII 题材**，且导演层是为这一部片子调校的，不是通用引擎。
6. **无 CI 真实运行过**（workflow 已本地验证，没有远端仓库）。

## 判断（明确标为判断）

**论字符渲染质量本身**：成熟库大概比我们好。它们把全部精力投在这一件事上，
而我们 30k 行里大半花在因果、身份、契约、可复现上。**这一点我不打算辩解。**

**论「字符作为有身份的演员」**：这恰好是转码器**架构上无法**做到的事。
一部能记住「这一格字符是从哪个字母来的、经历了几次形变、还活着吗」的片子，
用 image→ascii 的管线做不出来，因为那条管线里**没有可碎裂的对象，只有可重新发射的像素**。

**结论**：
> 我们在**渲染质量**上大概率不如成熟库；在**叙事能力**上做的事情它们不做。
> **如果目标是「好看的 ASCII 画面」，应该直接用成熟库。**
> **如果目标是「字符自己演一部有因果的片子」，这个引擎是目前唯一有的东西——但它还没好看。**

## 这一轮之后的变化（对比我上一轮的回答）

上一轮我答这个问题时，**还没看过任何一帧、也没量过像素**，那是凭功能和印象在答。
现在能说的具体差异：

| | 上一轮 | 现在 |
|---|---|---|
| 平均墨覆盖 | 0.0197（稀疏、发灰） | **0.1248** |
| 峰值帧位置 | 帧 44（**开场**，叙事上错误） | **帧 292（碎裂段）** |
| 碎裂段密度 | 0.0117（**全片最暗**） | **0.2944（全片最亮）** |
| 是否看过画面 | 否 | 是（帧 311 / 330） |

**但表示变化（`SCENE_ASCII → TYPOGRAPHIC_GRAPHIC → GLYPH_FIELD`）仍未接入**，
所以片中有密度，**没有「质料本身在变」**——而那正是 V1 研究 C 最强的地方，也是我们相对成熟库最该拿出的东西。
